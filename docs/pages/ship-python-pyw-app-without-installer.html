Shipping a Python app to Windows users with no installer

The default answer is "freeze it with PyInstaller and ship a 30 MB .exe". For a small tool that is usually the wrong trade, and the reason is not size.

Why .pyw and not .py

On Windows, .py files are launched with python.exe, which opens a console window behind your GUI. .pyw files are launched with pythonw.exe, which does not. Renaming the file is the entire fix.

The catch: when pythonw.exe crashes, the traceback goes nowhere. You get a window that does not appear, and no error. During development, run it with python so you can see the traceback, and only ship the .pyw name.

Why not PyInstaller

A frozen build is a 10–30 MB executable that unpacks itself into a temp directory on every launch. Three practical consequences:

  • Antivirus noise. Self-extracting, unsigned executables are the shape of a malware dropper. Users report false positives, and you spend your time explaining instead of shipping.
  • Slow start. Unpacking tens of megabytes takes more than the app needs to draw a window.
  • It hides the source, which for an open-source tool that claims "no network code, read it yourself" is exactly backwards.

Freezing makes sense when your users cannot install Python, or when you ship a native dependency that is painful to build. Neither is true here.

What "no install" costs the user

Be honest about this, because it is the real price:

  • They must have Python 3.8+ already. That is a smaller group than developers assume, and a much larger group than it was five years ago.
  • They must unzip, not run a setup wizard. Usually fine; occasionally confusing.
  • There is no Start-menu entry, no uninstaller, and nothing in "Apps & features". Deleting the folder is the uninstall — which some people find uncomfortable.
  • File associations and "Open with" never point at it.

None of those are fatal for a personal tool. All of them are worth stating on the download page instead of letting people discover them.

A folder layout that survives moving

Keep the program and its data together, and resolve paths relative to the script rather than the working directory — otherwise a shortcut with a different "Start in" value writes your data somewhere unexpected:

desktop-plan-widget/
├─ plan_card.pyw          # double-click this
├─ tools/                 # data layer, i18n
├─ sample/                # demo data, seeded on first run
└─ plan_data.json         # created next to the script on first save
ROOT = os.path.dirname(os.path.abspath(__file__))
PATH = os.path.join(ROOT, "plan_data.json")

Two lines, and the tool works from any working directory, any drive, any user profile.

Getting found anyway: winget and portables

Users do search package managers, and listing there does not require an installer — a portable manifest points at a zip and a command to run. The repository keeps the manifest skeleton in packaging/winget/ with the fields that need filling in marked as such.

Two things to know before you try: winget manifests are validated against the published URL's hash, so you bump the manifest on every release; and Chocolatey is a separate (community-reviewed) submission with its own rules. Neither is a one-time job, which is why most small tools never do it.

When to freeze instead

Freeze when the tool must run on machines where users cannot install anything — a corporate image, a school lab — or when your dependency tree includes something compiled. For a single-file stdlib tool, the zip is better for everyone: smaller, faster, inspectable, and impossible to get flagged as a dropper.
